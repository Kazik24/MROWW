# Redpilator optimization implementation briefs

Each numbered section is one agent assignment. Start each experiment from the same recorded revision and working-tree state. The reviewed commit was `db4b1531`. Existing local changes affect compile admission and memory accounting, so record the baseline patch used for memory measurements. Separate worktrees and private LLVM cache directories let agents build independently. Reserve the benchmark machine for one timed experiment at a time.

## 1. Charge complete conditional movement ranges once

**Objective.** Improve strict ZCore simulation throughput by removing per-flip operation accounting when an entire selected range can execute. A 5,000-tick trace recorded 9,150,111 scalar fallback flips. This is a count of operations across the trace. The distribution of range lengths determines how much accounting can actually be saved. [Movement profile](../test_data/cpu-references/experiment3-movement-kernels.md)

**Owner and scope.** Work in `set_token_pos` in [llvm_movement.c](../crates/core/src/redpilator/sampled/llvm/llvm_movement.c). Target the canonical conditional loop immediately after the group state is committed. Flat replay and active graph replay already charge complete ranges. The existing scalar path is the reference for a partial range.

1. In a diagnostic build, count entries to this specific loop, total flips, empty and singleton ranges, and ranges that exceed the remaining budget. Collect strict ZCore after its 413 preparation ticks. Record how many per-flip checks a range check could remove. Stop if almost all visits are empty or singleton and the profile shows negligible time here.
2. After group validation and canonical range selection, compare its length with the remaining budget. On a complete fit, add the length to both counters and replay the same canonical records through `apply_movement_flip` in order. Verify that the flip helper and its callees cannot fail, observe either counter, or reenter execution between flips. For insufficient budget retain the existing `consume` loop, including the failed operation's counter increment. Preserve graph materialization and group-state visibility on failure.
3. Exercise an actual conditional range of length at least two, on arrival and departure. Inject budgets from zero through length plus one and compare baseline/candidate snapshots, work count, error and completed tick prefix. Adapt the existing guard harness to inject at the **conditional loop**. Its original fixed-range injection alone cannot exercise this change. Run the native/Rust per-tick ZCore motion comparison and check relaxed graph replay as a regression workload. [Guard harness](../crates/core/examples/experiment_movement_kernel_guards.rs) · [Native regression tests](../crates/core/src/redpilator/sampled/llvm/tests.rs)
4. Inspect optimized IR or disassembly for the successful loop, then time uninstrumented builds with `bench_engine_compare` on strict ZCore for 50,000 ticks. Use relaxed ZCore and active PM1 as regression cases. Apply the runtime decision criteria below. Deliver the range histogram, prefix comparisons and paired timings. [ZCore runner](../crates/core/examples/bench_engine_compare.rs)

## 2. Skip redundant scans in reactive output programs

**Objective.** Improve active PM1 throughput by exposing contribution/callback boundaries already present in immutable output ranges. In the saved relaxed PM1 program, 12,563 distinct nonempty ranges contain only contributions, 13,066 have contributions followed by callbacks, and 8,985 interleave them. A range used once and a range used every tick count equally in that census.

**Owner and scope.** Own `execute_output` in [engine.c](../crates/core/src/redpilator/sampled/llvm/engine.c) and any new reactive-range metadata in [generated.rs](../crates/core/src/redpilator/sampled/llvm/generated.rs). Agent 3 owns movement-step packing and the existing table writer in that Rust file. Keep edits to those shared areas in separate hunks.

1. Classify both rise and fall ranges by opcode, using the same contribution predicate as the existing first pass. Instrument active PM1 SORT to count calls **and records visited** by class, including empty and callback-only ranges. Report removable visits and sample time in `execute_output`. If eligible ranges are cold or mostly too short to repay a metadata load, deliver the census and stop before adding production metadata.
2. Prototype the cheapest useful class first. Contribution-only ranges can finish after staging contributions and calling the existing final reactive update. If split ranges account for substantial work, derive a split offset at generation time and run the contribution prefix and callback suffix directly. Preserve both contribution kinds, changed-target invalidation, the callback suppression predicate, callback order, work charging and the first error. Use the existing two-pass path for interleaved ranges and the existing single pass for nonreactive programs. Bound and report metadata bytes, especially for shared ranges. Keep the generic C build usable.
3. Cover all five classes on both edges, including shared ranges, an arrangement contribution and a suppressed reactive callback. Inject failure in the contribution prefix and in the callback suffix. Compare the resulting state, ordered effects, pending work and counters with the original native path. Exercise the normal Rust-to-generated-module entry point as well as focused cases. [Existing native test fixtures](../crates/core/src/redpilator/sampled/llvm/tests.rs)
4. Run `bench_pm1_compare` with the saved PM1 protocol, its frozen reference, one Start press, command blocks enabled and all 12,070 ticks. Validate the ordered 1,534 messages, RAM, lamps, screen and halt. Use relaxed PM1 as the primary timing, strict PM1 and strict ZCore as regressions. Inspect the emitted loop for an eligible range. Deliver weighted coverage, module and metadata size changes, and paired timings. [PM1 runner](../crates/core/examples/bench_pm1_compare.rs) · [Protocol](../test_data/cpu-references/pm1_redpilator_protocol.json) · [Reference](../test_data/cpu-references/pm1_redpilator_reference.json)

## 3. Reduce temporary memory during native table emission

**Objective.** Reduce host memory allocated while emitting a cold native module. In the saved relaxed PM1 build the movement-step table was 10,216,960 bytes and the largest derived word table was 41,241,600 bytes. The two allocations have different lifetimes. Measure phase and process peaks independently.

**Owner and scope.** Own `direct_movement_ranges`, its caller, the derived-word-table write loop and their focused tests in [generated.rs](../crates/core/src/redpilator/sampled/llvm/generated.rs). Use the existing allocator, cache ownership rules, cancellation and build manifest. The encoded table layout and generated C interface are compatibility requirements.

1. Record a cold relaxed PM1 baseline with direct ranges active. Capture host allocations or high-water memory during Rust emission, whole-build peak including Clang, emission time from the manifest, and end-to-end wall time. Hash `program.h` and all generated `.bin` files. Use fresh owned cache directories for each build and hold the world snapshot, toolchain and allocator configuration fixed.
2. Remove the `steps.to_vec()` copy. Let the helper pack the caller's mutable movement-step rows in place after the representability check succeeds. Its rejected path must leave the input untouched for canonical replay. Extend the existing direct-range test to check both accepted packed words and unchanged input on rejection.
3. Replace the derived-table write site's whole-table `bytes(words)` allocation with bounded little-endian conversion and sequential writes. Keep small descriptor and test uses of `bytes` as appropriate. Propagate write and final flush failures before allowing a build to complete. Compare emitted bytes for an empty table, a short table and a table spanning multiple chunks with a partial final chunk.
4. Compare baseline/candidate file hashes for strict and relaxed PM1, including a case without direct ranges. Load both generated modules and compare program identity and frozen simulation results. Cache keys can legitimately differ because the generator source is hashed. Repeat cold builds in alternating order, reporting host emission peak, build peak and elapsed time for each. If Clang dominates the overall peak, report the host-only result separately. Keep each edit on its own merits if it demonstrably reduces temporary allocation with identical output and no repeatable material compile slowdown. [Cache and manifest](../crates/core/src/redpilator/sampled/llvm/cache.rs)

## Runtime decision and handoff

For agents 1 and 2, use matched stimuli, identical batch size, publication settings and warmup. Build before timing. Compare fresh executors in alternating or balanced order, retain raw samples and use at least five pairs for confirmation. Run a byte-identical separate-image null control on the timing setup. Earlier controls produced apparent gains as large as 2.93%, and the crossover calibration was incomplete. If the control cannot resolve the engineering threshold, report the timing as inconclusive. The existing plan calls for a reproducible 3% gain and a 2% regression limit, with broader fixture and live-publication confirmation before general adoption. [Optimization plan](REDPILATOR_OPTIMIZATION_PLAN.md) · [Crossover status](../test_data/cpu-references/experiment4-image-crossover.md)

Each agent returns its patch or a documented stop decision, exact revision and build commands, correctness results, raw measurement locations, and a retain/reject/inconclusive verdict. Use private diagnostic builds for counters and injected limits. Compare each candidate against the common baseline first. If both runtime changes qualify separately, repeat correctness and timing on the combined build before attributing a combined gain.
